# Как я подключил Яндекс Почту к ChatGPT через MCP, ZimaOS и Authentik

Я хотел работать с почтой из чата: находить нужные письма, читать переписку и по явному запросу переносить сообщения в архив. При этом сервер доступа к ящику должен был работать на моём ZimaOS, а возможность отправлять и удалять письма мне вообще не требовалась.

В результате получился небольшой Python-сервис: Яндекс Почта по IMAP с одной стороны, MCP Streamable HTTP — с другой. Для подключения ChatGPT я использовал Authentik. По пути пришлось разобраться с OAuth, доступом к собственному домену из домашней сети и контейнером, который не мог прочитать свой server.py.

В статье покажу устройство решения, ограничения и несколько ошибок, на которых легко потерять время. [Код, Docker Compose и подробные инструкции опубликованы на GitHub](https://github.com/mars485/yandex-mail-mcp).

## Задача: один ящик и шесть операций

Я сознательно ограничил интерфейс шестью инструментами:

| Инструмент | Что делает |
|---|---|
| list_folders | Показывает папки |
| search_messages | Ищет письма по тексту, отправителю, теме, датам и признаку непрочитанного |
| read_message | Читает выбранное письмо |
| mark_read | Помечает его прочитанным |
| move_message | Переносит в существующую папку |
| archive_message | Переносит в настроенную папку архива |

SMTP здесь нет. Отдельного удаления тоже нет. Это не делает любые действия безрисковыми: перенос всё равно меняет почтовый ящик, поэтому я разделил чтение и запись на уровне разрешений сервера.

Ещё одно существенное ограничение: сервер обслуживает один ящик, указанный в настройках. Если разрешить вход другому пользователю Authentik, он получит доступ к этому же ящику. Это не сервис индивидуальной почты для всей семьи или компании.

## Как устроено подключение

```text
ChatGPT → HTTPS reverse proxy → ZimaOS:8822 → MCP-контейнер:8000
                                                     ↓
                                              IMAP TLS:993
                                                     ↓
                                                Яндекс Почта

ChatGPT → Authentik → access token → проверка подписи на MCP-сервере
```

Сервис использует официальный Python SDK `mcp==2.2.0`. Здесь важно различать версию библиотеки и версию протокола: цифра 2 в имени версии SDK не означает отдельный «протокол MCP 2».

Для удалённого клиента выбран Streamable HTTP. SDK предоставляет ASGI-приложение, которое запускается через Uvicorn; описание этого интерфейса есть в [документации Python SDK](https://py.sdk.modelcontextprotocol.io/run/asgi/). Docker публикует порт 8822 хоста на 8000 контейнера, а HTTPS завершает reverse proxy.

Почтовый пароль приложения хранится в `.env` на сервере. В репозиторий и образ он не попадает. На каждую операцию открывается отдельное IMAP-соединение с проверкой TLS-сертификата. Локальной базы с копиями писем нет.

Однако self-hosted здесь относится к серверу интеграции. Когда я прошу ChatGPT прочитать письмо, его содержимое передаётся клиенту и модели. Это не способ гарантировать, что переписка никогда не покинет домашний сервер.

## Почему рабочего Bearer-токена оказалось недостаточно

Сначала сервер умел принимать статический `Authorization: Bearer ...`. Для собственного диагностического клиента этого достаточно: он знает секрет и отправляет заголовок.

Но в форме подключения ChatGPT я выбрал OAuth. Вставить статический MCP-токен вместо OAuth Client Secret нельзя: это разные значения с разными назначениями. Client Secret нужен OAuth-клиенту для обмена с сервером авторизации; access token даёт доступ к ресурсу.

В моей схеме Authentik отвечает за вход и выдачу токенов, а MCP — за их проверку. Для такой интеграции нужны согласованные метаданные ресурса и сервера авторизации; требования описаны в [документации OpenAI по аутентификации MCP](https://developers.openai.com/plugins/build/auth).

Я создал отдельное приложение Authentik, настроил RSA-подпись и redirect URI из текущей формы ChatGPT. Callback нужно именно копировать из формы: значение старого подключения не стоит считать постоянным. Для OAuth используется authorization code с PKCE S256. Адреса endpoints и особенности issuer приведены в [документации Authentik](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/).

Серверу MCP Client Secret не нужен. Он получает публичные ключи JWKS и проверяет подпись access token. В дополнение к подписи проверяются issuer, audience нашего ресурса, Client ID в azp, сроки действия, необходимые claims и разрешения.

## Разрешить вход — ещё не значит разрешить запись

Я использовал две группы:

- `yandex-mail-mcp-users` — доступ к ящику;
- `yandex-mail-mcp-writers` — дополнительное право менять письма.

Группа users привязана к приложению как разрешённая. Writers не добавляется отдельной разрешающей привязкой: одной этой группы недостаточно для доступа.

В scope mappings выдаются признаки `mcp_read` и `mcp_write`. Для чтения сервер требует одновременно scope `mail:read` и `mcp_read=true`. Для записи — ещё `mail:write` и `mcp_write=true`. Над всем этим действует `MCP_ENABLE_WRITE=false`: он запрещает запись независимо от OAuth-прав.

Это именно серверная проверка. Аннотация инструмента readOnlyHint помогает клиенту понять намерение операции, но сама по себе не является механизмом доступа.

У схемы есть компромисс: JWT проверяется локально, без запроса introspection при каждом обращении. Удаление пользователя из группы не аннулирует уже выданный токен немедленно. Поэтому в инструкции рекомендован короткий срок access token, например пять минут. Допуск часов в валидаторе — десять секунд. Для немедленного отключения OAuth можно выключить этот режим и пересоздать контейнер; статические ключи при этом требуют отдельного отзыва.

## Чтение почты тоже может менять почту

При работе с IMAP недостаточно назвать инструмент «чтением». Обычное получение тела письма может поставить флаг Seen.

В сервисе чтение выбирает папку в read-only режиме и использует BODY.PEEK. Отметка прочитанного вынесена в отдельную команду. Вложения возвращаются только как метаданные; сервер их не выполняет и не предоставляет отдельное скачивание. Для размера MIME и выдаваемого текста установлены ограничения.

Для операций записи нужен не только UID письма, но и UIDVALIDITY папки. UID не является вечным идентификатором во всём ящике. После изменения состояния папки старое значение может потерять смысл. Поэтому клиент сначала выполняет поиск, а затем передаёт полученные UID и UIDVALIDITY в команду записи.

Перемещение использует native UID MOVE. Если сервер его не поддерживает, операция отклоняется. Fallback через COPY, удаление и EXPUNGE здесь не реализован: мне важнее предсказуемый отказ, чем более широкая совместимость ценой дополнительных побочных эффектов.

После сетевой ошибки результат записи может быть неизвестен: сервер успел выполнить MOVE, но ответ не дошёл. Автоматический повтор в этом случае — плохая идея. Сначала нужно проверить исходную и целевую папки.

## Ошибка № 1: внутри всё работает, через домен — timeout

Локальная проверка проходила: MCP отвечал, авторизация работала, IMAP возвращал папки. Запрос к внешнему HTTPS-адресу с того же ZimaOS завершался таймаутом.

Полезным оказалось разделить проверку приложения и маршрута. Для обращения к LAN-адресу reverse proxy с сохранением доменного имени я использовал `--resolve`:

```bash
curl --connect-timeout 5 --max-time 10 \
  --resolve mail-mcp.example.com:443:192.168.1.10 \
  https://mail-mcp.example.com/health
```

Домен и IP здесь примерные. Имя остаётся в TLS-проверке, а соединение идёт по заданному адресу. Этот запрос вернул 200. Значит, переписывать MCP из-за таймаута было бы преждевременно: локальный HTTPS-маршрут до приложения уже работал.

Для доступа контейнера к доменам через LAN можно использовать split DNS или локальный Compose override с extra_hosts. Это не заменяет внешний доступ: клиенту ChatGPT всё равно нужен достижимый HTTPS endpoint. И это не повод отключать проверку сертификата.

## Ошибка № 2: контейнер не может прочитать собственный файл

Следующая проблема выглядела так:

```text
python: can't open file '/app/server.py': [Errno 13] Permission denied
```

Контейнер постоянно перезапускался, поэтому запустить smoke test через exec было невозможно. Причина оказалась в правах файлов комплекта и непривилегированном пользователе контейнера.

Исправление добавлено в Dockerfile:

```dockerfile
RUN chmod 0755 /app && chmod 0644 /app/*.py /app/requirements.txt
USER 10001:10001
```

Исходники можно читать, но сервис по-прежнему работает не от root. Для распространяемого ZIP также явно задаются Unix-права файлов. Такая мелочь особенно заметна, когда архив готовится на Windows, а запуск происходит на Linux.

## Проверки, которые действительно помогают

У проекта два разных диагностических сценария. `smoke_test.py` проверяет 401 без токена, инициализацию MCP, набор инструментов и при `--imap` чтение папок. `oauth_check.py` проверяет discovery, scopes и публичные ключи Authentik. Ни один из них не меняет письма.

Но успешный discovery не доказывает, что конкретный пользователь получит правильные claims. Полный OAuth-вход и доступ нужно проверять через клиент отдельно.

В подготовленной публичной версии прошли 43 автоматических теста. Они используют фиктивный IMAP и временные RSA-ключи: проверяют разрешения, отклонение некорректных токенов, протокольные вызовы и операции с почтой без подключения к настоящему ящику. Это не аудит безопасности и не доказательство совместимости с любой версией Authentik. Подробные границы проверки записаны в VALIDATION.md. Моя персональная установка на ZimaOS после настройки работает; публичная версия дополнительно выносит адреса и Client ID в переменные окружения.

Логи намеренно скучные: тип события и имя инструмента, без токенов, тела письма и исходных исключений библиотек. Это усложняет некоторые разборы, зато диагностика не становится ещё одной копией приватной переписки. Логи reverse proxy нужно контролировать отдельно.

## Что получилось и чего здесь пока нет

Получилась небольшая интеграция для одного ящика с явной границей между чтением и изменением писем. Её можно начать использовать только для поиска и чтения, а запись включить после отдельной проверки.

Здесь нет многопользовательских почтовых аккаунтов, полнотекстового индекса, фоновой синхронизации, обработки вложений и мгновенного отзыва JWT. Ограничения существуют и у модели: содержимое входящих писем нельзя считать доверенной инструкцией. Отсутствие инструмента удаления не отменяет необходимости подтверждать изменения.

[Репозиторий Yandex Mail MCP](https://github.com/mars485/yandex-mail-mcp) содержит исходники, Compose, шаблон env, инструкцию Authentik и диагностику. Личные домены, адреса, callback и Client ID заменены настройками и примерами. Если повторять установку, я бы начал с локального smoke test, затем проверил внешний HTTPS и только после этого переходил к OAuth и правам записи.
